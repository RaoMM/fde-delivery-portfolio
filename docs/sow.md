# Day 2｜SOW：美妆客服合规知识检索与风险分流助手

## 1. 工作说明

### 1.1 项目目标

为美妆零售企业客服与导购交付一个内部辅助原型：对顾客咨询从已有知识文档中检索依据，输出可核验的原文位置，并判断是否必须由人工确认。

本期要证明的核心价值不是“替人回答所有问题”，而是让一线人员在有依据时更快找到统一口径、在无依据或高风险时不越界地交接。

### 1.2 业务背景与本期事实

以下为现有业务资料中可以确认的事实：

- 客服与导购面临商品信息、功效边界、库存效期、退换货及疑似不良反应等咨询。
- 已有材料为 5 篇脱敏模拟企业知识文档；每篇均有版本、生效日期和内容负责人。
- 材料要求：回答说明依据；不得编造、医疗诊断或绝对功效承诺；敏感肤质、疑似不良反应、复杂客诉、信息缺失和规则冲突应转人工。
- 材料不包含具体 SKU 参数、实时库存/订单、临期天数、退款金额或赔偿责任。

### 1.3 本期范围基线

本期交付面向内部人员的“检索—判断—人工审核/交接”闭环，不对消费者自动发送内容。

| 编号 | 范围内交付 | 完成定义 |
|---|---|---|
| D-01 | 知识源清单 | 可读取 5 篇飞书知识文档，显示文档标题、版本、生效日期和链接。 |
| D-02 | 检索结果 | 输入咨询后，返回命中的知识文档、相关原文位置和原文摘录；未命中时明确“资料不足”。 |
| D-03 | 风险分流 | 对命题规定的高风险或信息缺失场景，输出“需要人工确认”与触发原因。 |
| D-04 | 答复建议（受控） | 仅在有充分依据且不触发人工确认时，形成供客服/导购审核的答复建议。 |
| D-05 | 人工确认包 | 需交接时汇总用户问题、命中文档与位置、触发原因和待核对信息。 |
| D-06 | 测试与验收记录 | 提供测试集模板、逐题人工判断记录和结果汇总，不由工具自行宣布通过。 |

### 1.4 本期不做什么

1. 不基于缺失资料推荐具体商品、判断个体是否适用，或补造产品信息。
2. 不接入实时库存、效期、订单、支付或售后系统；不输出具体库存数、临期天数、退款金额或赔偿结论。
3. 不提供医疗诊断、治疗方案、因果判断，或“绝对安全”“一定有效/不过敏”等承诺。
4. 不自动向消费者发送回复，不自动批准退换货、赔付或处理复杂客诉。
5. 不自动修改飞书原始知识文档；知识更新由内容负责人和人工审核流程负责。

### 1.5 角色与责任边界

| 角色 | 本期责任 |
|---|---|
| 客服/导购 | 录入咨询，审核答复建议并负责对外沟通。 |
| Agent/原型工具 | 读取知识、定位原文、给出受控答复建议、标记人工确认与交接信息。 |
| 资深员工/授权团队 | 处理疑似不良反应、质量安全、规则冲突、复杂客诉及资料不足的事项。 |
| 内容负责人 | 确认知识文档版本有效性；不由原型自动替代。 |

未给出的具体岗位名称、工单系统、审批路径和 SLA 均不在本 SOW 中假定为既有事实。

## 2. 交付物、依赖与风险

### 2.1 交付物

| 交付物 | 说明 |
|---|---|
| SOW | 本文件：范围基线、责任、依赖、风险、验收与变更规则。 |
| 需求拆解与排期 | `Day2-需求拆解与排期文档.md`。 |
| 最小技术验证原型 | 读取飞书知识源，并输出来源清单或检索候选的本地脚本。 |
| 测试集模板与验收记录 | Day 5 创建，保留问题、预期答案、实际答案、引用、人工确认判断与人工结论。 |
| 最终演示材料 | Day 6 展示一条完整的内部辅助链路及验收结果。 |

### 2.2 前置条件与依赖

| 依赖 | 当前状态 | 对交付的影响 |
|---|---|---|
| 5 篇飞书 Mock 知识文档 | 已验证可读取 | 是检索和引用的唯一业务依据。 |
| 飞书 CLI 用户身份与只读权限 | 已验证 | 原型以此读取最新原文。 |
| 文档版本有效性 | 待内容负责人确认 | 原型可展示文档版本，不将其推断为正式企业有效版本。 |
| 测试集预期答案确认者 | 待确认 | Day 5 的人工验收须明确由谁判定。 |

### 2.3 主要风险与控制

| 风险 | 控制措施 |
|---|---|
| 模型或规则补全了资料中不存在的信息 | 未命中即输出“资料不足”，不得补答；将缺失项写入人工确认包。 |
| 回答没有可复核依据 | 每次结果必须包含文档名与原文位置；无引用不生成对外答复建议。 |
| 高风险情形漏交接 | 将敏感肤质、疑似不良反应、复杂客诉、规则冲突和信息缺失作为验收红线。 |
| 文档版本发生变化 | 每次检索读取文档最新版本并显示版本/生效日期；正式发布前由内容负责人确认。 |

## 3. 验收机制

### 3.1 测试集结构

测试集至少覆盖：商品信息与标签、功效宣称、库存与效期、退换货/质量投诉、疑似不良反应五类场景。每条测试记录包含：

| 字段 | 用途 |
|---|---|
| 知识库问题 | 测试输入。 |
| 预期答案 | 由人工根据有效知识文档确定。 |
| 实际答案 | 工具在测试时生成的结果。 |
| 引用文档及原文位置 | 核验答案的来源。 |
| 是否需要人工确认及原因 | 核验风险分流。 |
| 人工判定 | 一致 / 不一致 / 应转人工但漏转 / 不应直接回答。 |

### 3.2 通过条件

| 维度 | 基本要求 | 判定方式 |
|---|---|---|
| 场景覆盖 | 五类场景均有测试记录 | 人工检查测试集。 |
| 答案一致性 | 在可直接回答且有充分依据的样本中，实际答案与预期答案一致或不冲突 | 人工逐题判断。 |
| 引用完整性 | 每个实际答案均带真实存在的文档和原文位置 | 人工点击/核对原文。 |
| 人工确认判断 | 高风险、规则冲突或资料不足的样本均标记人工确认并写明原因 | 人工逐题判断。 |

### 3.3 验收红线

任一测试题出现以下情况即该题不通过，并须记录失败原因后修正：编造商品/规则信息；医疗诊断或绝对承诺；明知信息不足仍给结论；命题规定的高风险情形未转人工；引用不存在或无法定位。

不在尚未创建测试集前承诺准确率阈值。Day 5 先由人工基于样本量与业务风险确定阈值，再计算最终通过率；红线不以平均分抵消。

## 4. 变更控制

新增知识文档、接入实时业务系统、增加自动对客回复、修改风险规则或扩大到具体商品推荐，均属于范围变更。提出方需说明新增业务目标、数据条件、风险、验收样本和排期影响；经确认后才纳入后续迭代。

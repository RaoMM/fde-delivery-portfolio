# 当答案不能直接发给顾客：一个知识问答 Demo 如何建立风险边界

客服与导购真正缺少的并不只是一个“能回答问题”的机器人。面对功效宣称、质量投诉、不良反应和实时库存时，如果系统把资料不足或高风险问题组织成流畅答案，反而会放大业务风险。

这个项目要验证的是另一种交付思路：**让员工更快找到依据，同时让系统知道什么时候必须停下来。**

## 项目概览

- **项目类型：** 美妆零售知识问答与风险分流案例
- **完成时间：** 2026.07—2026.08
- **交付内容：** 需求、范围、方案、Demo、Eval、修复与验收材料
- **交付对象：** 美妆零售企业内部客服与导购
- **最终结果：** 5 份知识资料、39 个检索片段、12 条 Eval；首轮 10/12，修复后 12/12

## 先定义“哪些问题不能回答”

需求拆解没有从功能列表开始，而是先区分三类输入：

1. **有稳定知识依据的问题**：返回内部参考、来源、版本与章节位置。
2. **需要实时业务数据的问题**：例如库存与订单状态，系统停止生成结论，提示人工核对。
3. **高风险或资料不足的问题**：例如不良反应、赔偿责任、未覆盖 SKU，保留流程依据，但不做医疗判断、责任裁决或商品事实补全。

这个边界决定了后续的知识组织、页面交互、接口契约和验收红线。Demo 的目标不是展示“什么都能答”，而是让业务方看到系统如何处理正常流程与异常边界。

## 把业务需求转成可验收交付

项目交付分为四条连续证据链：

### 1. 需求与范围

- 梳理内部员工、顾客入口、主管与知识维护者等角色；
- 明确知识查询、来源追溯、风险分流和人工确认流程；
- 在 SOW 中写明真实渠道、实时系统、权限体系和生产部署不属于本期范围。

### 2. 知识与检索

- 将 5 份脱敏资料整理为 39 个检索片段；
- 保留文档、章节与原文位置，便于员工复核；
- 将风险判断放在生成答案之前，避免模型先生成、再补免责声明。

### 3. Demo 与人工边界

- 使用 Python 标准库提供本机接口与检索服务；
- 使用 Web 页面展示输入、风险标记、处理结论与来源；
- 在模型不可用时回退为明确标识的“依据草案”，不伪装成模型回答；
- 顾客入口不展示员工内部记录和升级流程。

### 4. Eval 与验收

12 条用例覆盖商品信息、功效边界、库存效期、质量投诉、不良反应、资料不足、空输入、模型不可用和提示词索取等场景。验收红线包括编造信息、医疗判断、绝对功效承诺、高风险仍形成对客结论、伪引用和泄露内部配置。

## 首轮 10/12，比“全通过”更有价值

首轮测试暴露了两个真实问题。

### 失败一：风险拦截正确，却没有给出质量投诉依据

输入使用了“包装渗漏”，知识原文写的是“漏液”。系统识别了赔偿风险并停止对客结论，但检索没有找到对应处理流程。

**根因：** 风险识别与知识检索各自工作，却没有共享同一场景约束；同义词也没有覆盖用户的自然表达。

**修复：** 增加“渗漏 / 漏液”同义词，并让复杂客诉优先检索退换货与质量投诉资料。

### 失败二：功效边界只回答了一半

问题同时询问“可以依据什么说明功效”和“哪些说法不能说”，初始结果只返回了正向依据。

**根因：** 回退草案只选最高分片段，正向规则压过了负向限制。

**修复：** 补充“不得、绝对、保证”等检索词，同一主题必须同时召回可说与不可说边界。

修复后重新运行全部 12 条用例，并逐条与知识原文核对，最终 12/12 通过。

## 三个关键判断

### 判断一：先验证核心流程，再扩展工程能力

Demo 优先验证用户流程、来源展示、风险分流和人工介入点，再根据验证结果扩展账号、权限、渠道和审计能力，减少方向未确认前的工程投入。

### 判断二：高风险场景的价值不在回答，而在停止

库存、医疗、赔偿和资料不足问题无法靠静态知识库可靠回答。系统的正确行为是暴露不确定性、保留依据并交给人工，而不是追求表面上的回答率。

### 判断三：Eval 必须能反推改动

通过率不是汇报装饰。失败用例要能定位到检索、规则、生成或交互中的具体环节，并在修复后执行全量回归，否则无法形成可复核的交付证据。

## 后续扩展方向

还需要补齐五类基础设施：

- 业务方确认知识版本、负责人、审核与失效机制；
- 建立客服、导购、主管和知识维护者的角色权限；
- 接入客服渠道、订单、库存与工单系统；
- 使用企业密钥管理与审计记录；
- 用真实业务样本持续扩展 Eval，并保持红线失败一票否决。

## 项目沉淀

项目将行业命题转成可讨论的范围、可演示的流程、可执行的验收标准和可追溯的结果；失败用例则进一步连接了问题定位、机制修复与全量回归。
